## Proposed PR title

Release 0.3.0: library-first studio, prompt conversion, refinement and evaluation

## What this changes

Replace the generate-and-history workflow with a library and one sections editor
for saving, filling and copying reusable XML-style prompts. Paste a working prompt
and review extracted variables with original values before copying or applying.
Refine with questions and a section diff; evaluate saved versions against reusable
cases and compare historical outputs. Apply/Undo and Save remain separate actions.

The release includes mobile section controls, direct library Fill and copy,
required/optional variables, opt-in examples, Try once, settings navigation,
model-compatibility guidance and provider/model charge notices. Backend and frontend
internals are reorganised without changing preserved REST/MCP behavior; intentional
contract changes are listed below and in the changelog.

Type of change: Feature · Breaking change · Docs · Refactor · Tests · Bug fix.
Related work: integration of the existing `dev` feature and refactoring branches.

## Upgrade and compatibility

- Rehearse against an isolated copy of a verified production backup before go-live.
  Startup applies migrations 023, 024 and 025 once, as described in
  [the deployment guide](../deployment.md#upgrading-to-030). Synthetic migration
  tests do not replace this production-data rehearsal.
- Migration 023 recovers sections from hand-edited prompt text and keeps the old
  state as a version. Migration 024 names and files old unnamed History records.
  Migration 025 corrects edit-note association, retains original `legacy_note`,
  stores the current note, and includes variable metadata in new snapshots.
  Restoring older snapshots retains current settings. Existing prompts and
  historical evaluations are preserved.
- Remove the obsolete weekly-summary cron entry. Refresh cached MCP schemas.
- Removed routes: prompt generate/history/tags, per-prompt Playground run/history,
  and analytics dashboard. Writes to `generated_prompt` and `tags` are rejected;
  responses omit tags/run count and profile notification preferences. See
  [the changelog](../../CHANGELOG.md) and [MCP contracts](../mcp.md#contract-changes-in-030).
- Existing `parse-text` callers keep fields-only output. Variable extraction
  requires `extract_variables: true`. Existing variables default to optional.
  Examples use existing JSON metadata and are explicitly saved separately.
- New editor API: snapshot refinement questions/draft and `POST /api/prompts/try`.
  Saved-prompt refinement routes remain compatible. Try once persists spend only.
- Migrations are forward-only. Reverting an image does not undo recovered data or
  note association. Rehearse backup restore and agree the post-backup data-loss
  window before any rollback. Do not run SQL reference files manually.

## Publication sequence after approval

1. After committing the preparation and merging locally, push the approved `dev`
   branch and create a PR with base `main` and head `dev`, using the title/description above.
2. Merge after review and required checks, retaining the integrated branch
   ancestry with a merge commit. Keep `dev` aligned with the final `main` commit. The current local merge is fast-forwardable; recheck if either moves.
3. On the approved merged release commit, create and push `v0.3.0`. Tag push,
   rather than merging to `main`, triggers image publication in `ci.yml`.
4. Wait for all tag checks and both GHCR image jobs. Record backend/frontend
   digests from their job summaries and pin deployment to the approved version
   or immutable digests. No floating `latest` tag is published.
5. Once the tag is published, date the 0.3.0 changelog entry with its actual
   publication date, add a fresh Unreleased section, and update compare links.
   Until then keep its notes under Unreleased, as CONTRIBUTING.md requires.
6. Deploy only after the backup rehearsal and deployment approval. Run the
   authenticated saved-prompt smoke checks in the deployment guide.

## Known limits

Model-discovery compatibility is guidance based on model names, not a portable
capability guarantee. Local AI tests use mocks; live-provider behavior is unverified.
A small configured-provider smoke check is recommended before go-live, after
reviewing provider/model and charge context. Review AI conversions and refinements for intent and content
fidelity. Converted inputs and staged review recover only in the current browser
and are cleared on sign-out; examples are saved only when explicitly chosen.
Evaluation grades outputs, with equally weighted averages of scored results;
failed/unscored cases are excluded and manual ratings must finish first.
